## 打开面板

双击项目根目录的 `启动截图建议.cmd`，或在项目目录运行：

```powershell
& .\.venv\Scripts\python.exe -m app.cli advise
```

2026-10-15 面板精简为四个按钮：**刷新雀魂窗口、整理窗口、开始自动建议、刷新截图**。保留游戏窗口和画面大小选择，删除底部说明、文件分析、人工核对、停止及自动整理勾选入口。开始自动建议时仍会自动整理窗口；关闭面板会停止后台任务。

候选操作只显示 Q 值最高的五项（不足五项时显示实际数量）。表格中的“相对评分”按这几项 Q 值的 softmax 归一化，最低保留 0.1%，显示一位小数，并按小数余量分配舍入差额，使合计恰好为 100%。例如 `100、-1、-1、-2、-2` 显示为 `99.6%、0.1%、0.1%、0.1%、0.1%`。这是便于比较的相对评分，不是胜率或真实操作概率；日志仍保留原始 Q 值，推荐动作不变。

点击“刷新截图”会重新获取所选雀魂窗口的当前画面并分析，无需选文件；没有开始自动建议时也可使用。自动建议已开始时，手动截图会取消旧请求，完成后继续监测后续行动；同一行动不会马上再自动分析一遍。手动截图保存到 `reports/screenshot-advice/manual-日期时间-请求号/`。按钮仍通过窗口图像接口取图，允许其他窗口遮挡游戏。

实时使用时，选择雀魂窗口和画面大小（1366×768 或 1920×1080），点击“开始自动建议”：按所选客户区尺寸调整游戏窗口、移到所在屏幕的左上方，并把建议面板摆到旁边。也可以单独点击“整理窗口”；屏幕放不下时选择较小画面。截图依据实际客户区边界，标题栏和边框不进入牌局图。保持默认牌面；系统显示缩放不影响尺寸校验，自动建议允许其他窗口遮挡游戏。更大窗口时，区域定位、计时器、文字和模板仍在缩放到 1366×768 的画面上运行（沿用已校准参数），只有牌种分类器读取原分辨率裁切；保存的截图为原分辨率。面板在背景线程读取窗口，检测右下角计时器区域的白色或橙色数字，只要求该区域有数字，不限制位数和秒数上限；支持 `293`、`15`、`0` 和 `4+20` 等显示，不要求两种颜色同时出现或特定数字组合。扩大识别范围以覆盖偏左的单数字位置；颜色及字形定位后再做 OCR。当前区域为客户区 `(1000,543,230,88)`。

后台通过 Windows.Graphics.Capture 持续接收指定游戏窗口的画面，只在内存中保留最新一帧，不保存视频。实时监测约每 150 毫秒裁切计时器、自己的手牌及自己牌河区域，不保存这些小区域，也不运行整局牌种网络。数字从未显示变为显示时，先等待 0.3 秒，给摸牌/副露动画留出短暂缓冲，再确认行动仍有效；若数字已经消失，则取消本次分析并立即恢复下一次触发能力。确认仍显示后，取当前完整客户区图并分析、保存及显示一次建议。连续两次确认数字消失时清除建议；持续显示且行动没有变化时不重复分析。连续两次确认倒计时重新上升至少 2 秒，或自己的手牌数量、独立摸牌槽、牌河牌位数量变化，也视为新行动：提前取消吃碰后直接摸牌、分析期间先出牌再轮到自己，都能重新触发。未知或短暂变化的牌体布局不用于重新触发。

推理结束、补截之前均复查上述行动依据；即使数字还在，只要已经是另一次行动，就丢弃过期结果并获取新局面。每次新行动开始先清空旧建议和候选，避免上一轮“跳过”或“打出某牌”留在新操作上。所有检查均保留计时器读数，检查中发现的新行动不会被吞掉。识别不完整时（手牌、摸牌、牌河、副露、宝牌区域有缺口，或响应来源未确认），只在同一行动仍有效时每隔 0.4 秒重取当前帧，最多 3 次，保留更完整的一帧。普通运行日志仍只把选中的那一帧写入 `action-NNNN`，`advice.json` 中的 `recaptures` 记录重试次数；补截后仍失败时，全部尝试另存为错误样本，详见下节。

## 自动保存识别错误

2026-10-17 新增。自动建议在同一行动中完成至少一次补截、最终仍无法确认局面时，自动归档初始截图和这一轮全部补截图。正常最多保存 4 张（初始图 + 3 次补截）；时间预算提前耗尽时，保存已经完成的全部尝试。补截后恢复成功、手动单次截图、用户停止或行动已变化的轮次不生成错误样本。每轮只归档一次，保存完成后面板显示“错误截图已自动保存”。

- 源码启动版：项目目录下的 `reports/recognition-errors/`。
- 便携测试版 3：`Majan.exe` 旁的 `userdata/recognition-errors/`。使用旧便携包时，请下载测试版 3 以包含本次功能。
- 文件按“运行编号 / action-NNNN”分组，同一次运行的多次失败分别保留；运行编号包含随机后缀，重新启动也不会覆盖旧样本。样本持续保留，不自动清理。

每个行动文件夹包含：

```text
manifest.json                    汇总、失败原因、补截次数、最终选中的尝试
00-initial.png                   初始原始截图
01-retry-01.png                  第一张补截图（后续依次编号）
00-initial.frame.json            初始截图的采集时间、尺寸、原始帧号等元数据
00-initial.recognition.json      初始截图的识别结果（每张截图都有对应文件）
capture-config-<SHA256>.json      采集和识别配置副本
final-result.json                本轮最终保留的识别结果
```

PNG 保留原始分辨率和像素；即使某次补截比初始图更差，也会保留。`manifest.json` 使用相对文件名引用各张图、元数据、识别结果及配置，并记录图片 SHA256；最后写入此清单表示一组样本已完整保存。普通运行日志与 `latest.json` 的 `failure_archive` 给出错误文件夹位置。目录不可写等保存错误会显示在面板和日志中，自动建议仍继续处理后续行动。

后续修正时，可以直接把整个行动文件夹作为问题样本交给开发流程，或在截图标注工具中打开其中一张原图，使用同目录配置复现。样本标记为 `unreviewed` / `debug`，自动识别结果保留为诊断信息，不能直接当作正确标签或训练真值。截图和诊断文件仅保存到本机。

验证：完整 **652 项测试通过**。另用现有真实 1920×1080 故障截图及其存档识别结果检查了四次尝试的保存和重载：原始像素一致、配置副本可被现有工具读取。该检查验证归档格式，不代表新增实战识别准确率验收。

自动建议优先读取指定 HWND 的窗口图像，不读取遮挡窗口，也不把游戏切到前台。主接口是 Windows.Graphics.Capture，`source` 为 `window_graphics_capture`，画面质量为 `window_content`；接口失败时尝试 PrintWindow，只有桌面客户区无遮挡时才允许退回屏幕截图。采集线程复制系统帧，按实际客户区裁掉标题栏和边框；黑屏、尺寸不匹配、超过 2 秒未更新的系统帧均不进入建议。游戏被其他窗口遮挡可以继续采集；最小化可能停止渲染，所以此时清除建议并暂停重试，不自动弹出游戏。恢复窗口后，采集会重新连接并重新确认行动计时器。关闭窗口或实际像素尺寸变化仍会提示；每 0.5 秒重试一次。人工标注采集和录制保留严格的无遮挡屏幕截图。

依赖已固定为 `windows-capture==2.0.1`，重建环境时按 `requirements.lock` 安装。为满足采集库依赖，项目使用标准 `opencv-python==4.11.0.86`，替代同版本 headless 包，避免两个包同时提供 `cv2`；图像处理版本保持 4.11.0。该库使用系统图像接口，不发送游戏操作。原理见 [微软窗口采集接口](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow)。验证结果见 `reports/window-content-capture/`；运行 `python -m scripts.verify_window_content_capture` 可复现完全遮挡后更新画面且不改变前台焦点的测试（普通 Windows 进程权限，非受限沙箱）。

## 响应速度（2026-10-15）

最新第二轮优化已启用认牌融合与混合精度模型，并对阈值临界结果做原精度复核。九张原始截图首次处理中位数约 **1.15 秒**；含当前 0.3 秒等待、行动复查和界面轮询预留的两个自动工作流回放约 **2.23 秒**，真实窗口采集和首次模型准备另计。2,457 张单牌和 20 个截图尺寸变体的牌种、确认结果、局面与建议通过原精度对照。原模型保留用于复核，原识别阈值不变。[加速说明与重建](pjura.md)、[当前测速](../reports/pjura-acceleration/advice-after.json)。下文保留第一轮 FP32 优化及缩短等待的历史条件和数据。

后续调整：截图前固定等待已由 0.7 秒缩短为 **0.3 秒**，每次正常触发减少 0.4 秒等待。行动复查、过期结果丢弃和识别不完整时的补截仍保留，相关 19 项时序检查通过；实际动画效果仍需实战观察。以下测速保留原 0.7 秒等待的历史条件，不将减少的时间冒充重新测量结果。

耗时主要来自牌面多角度网络识别、旧模板证据和文字读取；Mortal 决策通常只有十几至几十毫秒。过去 `total_ms` 只代表选中帧的一次分析，不包括此前的补截、0.7 秒动画等待及图片保存，不能作为整次操作的用时。

当前自动模式在等待行动前完成识别与决策模型预热。牌面完整证据按原裁切和原分辨率裁切的像素哈希、区域、阈值及旋转等参数缓存，最多 1,024 项；改变像素就重新识别，缓存不会放宽阈值或复用历史修正。网络预处理使用与原浮点舍入完全一致的查表，模型及所有旋转、透视校验保留。文字识别继续使用原 CPU 后端。

有效建议先送到面板，再保存原图、带框图及 JSON。补截按整次行动约 5 秒的预算安排；剩余时间不足以容纳一次估计分析时，返回当前识别缺口并提示刷新截图，不会把不完整局面转成建议。正在进行的一次推理不能强行中断，因此这是调度预算，不是任何机器负载下的硬性超时保证。日志新增 `latency`，记录从触发起的用时、全部分析累计耗时、分析次数和取图耗时；面板显示的用时还包括结果进入界面前的排队等待。

本机同一组 9 张原始截图、两轮回放中，首次处理的中位数为 3.00→2.21 秒，最大为 3.83→2.53 秒；原像素再次出现时的中位数为 2.52→0.095 秒。18 次识别内容、局面及推荐动作均与修改前一致。另用真实截图驱动实际自动建议工作线程，包含 0.7 秒等待、行动复查、补截逻辑，并预留 0.1 秒界面轮询：两个可建议场景约 3.82、3.84 秒；一个原本不能确认的场景约 2.74 秒返回缺口。这些测量不包含真实窗口采集延迟或实际动画变化；首次启动约 3 秒的模型准备单独记录。详情见 [测速数据](../reports/advice-performance/after.json)。

白板的空白字形只能确认牌种，不能证明旋转方向。白板碰牌优先使用明确的牌体横向比例；侧面透视使三个外框都显得竖长时，比较同组白板实际牌面两对边的平均长度，要求两张竖牌比例一致且唯一横牌的宽高比至少是另外两张的 1.5 倍。据横牌位置读取该座位的碰牌来源，证据保存在 `called_position_geometry`。缺少牌面轮廓、比例相近或多横牌时仍保留核对提示。

箭头遮挡（draft-18）：除先前无遮挡帧的像素核对缓存外，牌面至少一半未被箭头覆盖、网络候选和原模板指向同牌、三个既有训练分类器全票一致时，也可恢复已被主网络拒绝的字形。保留原网络读数与字形证据；不会把模板相似度写成网络概率。空白白板、五的颜色歧义、没有箭头或证据冲突不走这条恢复路径。桌面装饰形成宽碎块时，也必须同时缺少牌面轮廓、颜色不符合牌面且分类已拒绝，才从副露区排除。

本场和供托在界面上为零时不显示，所以这两个字段读不到时按 0 处理，不再当作识别缺口；其他文字字段仍然要求读到值。牌局文字（如“東1局”）由 OCR 和模板分别解析，两者得到同一个值即采用，单次读取分数不再是门槛，只有两者不一致或都解析失败才暂停。

吃碰和响应自动读取当前亮色操作按钮，并通过牌河末张牌周围唯一的绿色高亮确定刚出牌者。高亮会闪烁、颜色在淡绿到亮绿之间变化（HSV 色相约 53–93），并常被上一张牌和阴影挡住一边，所以按“末张牌外侧一圈中连成一片、横竖都包住这张牌的绿色光圈”判断；相邻索子牌面的绿色笔画只是零散短笔画，不会被当成高亮。按钮文字是书法字，OCR 常把“碰”读成“碟”，读不出时改按按钮底色判断：绿色为吃、青蓝为碰、红色为和（自摸/荣和按有无摸牌区分），其他颜色记为未识别的鸣牌按钮，交给规则引擎列出合法操作。按钮底色得出的操作必须与规则推算的可鸣操作一一对应（多种吃法只显示一个“吃”），不一致时暂停并请你核对，例如规则认为能荣和、但游戏因振听没有给出“和”。按钮从“跳過”向左最多排三个，按钮区域单独加宽（`buttons.banner_rect`，draft-15）。高亮会闪烁，暗的那一刻截到的画面里看不到；画面上有吃/碰/杠/和按钮却找不到高亮时，会和识别不完整一样每 0.4 秒补截，最多 3 次。等待鸣牌时，上一张弃牌上方会出现一个上下浮动的黄绿色箭头；在上家牌河里它正好盖住前一张牌的牌面。这张牌在之前自己行动时已经看清过，所以同一牌位、位置没变、箭头以外的像素也和当时一致时，沿用当时的读数（`evidence` 为 `earlier_unobstructed_reading_under_call_arrow`）。8 索、9 索这类绿色笔画很密的横向牌，亮色轮廓会被笔画切碎；如果候选框正好一个牌位大小、凸包仍覆盖一半以上，就当作牌保留，不再漏掉。牌河按顺序摆放，鸣走的牌不留空位，所以最后一张之前出现空牌位就说明漏检，此时牌河标为不完整。副露里的横牌看不出方向（如白板）时，用形状判断：三张里只有一张宽大于高，就把它当作横放的被鸣牌。场况文字由 OCR 和模板分别读取，两者都不够确定但读出同一个值（如“東1局”）时，采用这个值。只显示吃/碰/杠/和牌与跳过这些响应候选，不把响应阶段误认为吃碰后的弃牌；没有唯一高亮或按钮无法确认时，可在核对界面指定来源及可点操作。按钮白名单与规则掩码取交集，再参与推理。吃碰后无独立摸牌时，需要确认刚完成的副露，用于食替约束；仅有一组自己的副露时可以直接使用该组。复杂来源或未知杠结构仍需核对。

若建议立直，会同时返回“宣言后打出某牌”的条件建议；不会把这项建议执行到状态。已经按立直但还未弃牌时，可勾选核对对话框的对应状态，保证宣言弃牌保持听牌。临时振听按用户要求不追踪；牌河可计算的舍牌振听仍由规则引擎处理。
