## 三张图的真实内容（按现有识别核对）

- 图二：自己手牌 13 张（一万、二万、三万、赤五万、五万、七万、九万、三万筒、四万筒、六万筒、七万筒、东、东），无摸牌；四家牌河均识别完整；宝牌指示牌发财；东1局、余38。**手牌里没有七索或八索**，因此当前高亮的那张索子牌不可能是自己的吃牌对象。
- 图三：自己手牌 13 张（三万、四万、六万、七万、七万、八万、一万筒、二万筒、六万筒、一索、一索、西、发财）；对家（player 2，画面右方）副露识别为一组 6s/5s/7s。牌河有一处不完整。
- 图一：自己手牌与两家副露可读；自己牌河识别到 12 张，最后一张是九万，而九万同时出现在自己的吃副露（2p3p4p 之外的另一组）中，说明它已被鸣走。

## 根因

1. **高亮牌不在被识别的牌河列表里。** `app/vision/actions.py` 的 `highlighted_discard()` 只对“已识别出的牌河牌框”做逐框测量，并且要求高亮必须是该家牌河的**最后一张**。图二/图三里，被鸣走的那张牌本身没有被识别成牌河牌（它的牌面被高亮/青色底改变，分类器拒识），于是没有任何候选框可测，`reaction_discard.confirmed` 恒为 false。
2. **`highlighted_discard()` 只能返回座位来源，不能返回牌种。** 快照层随后用“该家牌河末张”作为响应牌；当高亮其实是该家倒数第二张、或末张未被识别时，两者不一致，直接报“请指定当前待响应弃牌的玩家”。
3. **吃之后的出牌阶段需要“刚完成的吃碰”来做食替检查。** 当自己有多组副露时，`melds` 的顺序是牌面布局顺序而不是鸣牌顺序，无法从单帧推断哪一组是刚完成的，所以这一条无法自动确定，只能让用户勾选。
4. **顺带发现：显示为零的供托/本场会被当成“识别不完整”而阻塞整条建议。** 实战三张图的本场、供托都读成 `D`/低分，导致 `honba`/`kyotaku` 区域 `complete=false`，`build_snapshot()` 直接抛错。
5. **顺带发现：牌局文字“東1局”的 OCR 与模板一致但分数略低于旧阈值（OCR 0.81、模板 0.86），被当成读取失败。**

## 本次修改

| 文件 | 修改 | 说明 |
| --- | --- | --- |
| `app/state/snapshot.py` | `honba`/`kyotaku` 在区域不完整时取 0 | 界面在数值为 0 时不画这两个字段，读不到就是 0；仍受数值范围校验 |
| `app/state/snapshot.py` | 吃按钮可以单独确定来源（自风左家） | 吃只能吃上家，规则上唯一；碰/杠/和仍需要高亮或人工指定 |
| `app/state/snapshot.py` | 高亮牌种为 `None`（只有座位）时不再与牌河末张比对 | 座位来源仍然有效，不因牌种未知而作废 |
| `app/vision/recognizer.py` | `AGREE_MIN_OCR` 0.7→0.75，`AGREE_MIN_TEMPLATE` 0.95→0.80 | OCR 与模板必须解析出同一个值才采用，分数只作为独立读者的门槛 |

## 仍未解决（需要实际对局继续核对）

1. **被鸣走的那张牌本身没有被识别成牌河牌**：这是图二/图三仍然停在“请指定当前待响应弃牌的玩家”的直接原因。已尝试四种判据，在真实画面上都不能稳定区分“高亮”与相邻索子牌的竹叶笔画／蓝色桌面：
   - 逐框描边密度（现有 `tile_glow`）：没有牌框就没有测量对象；
   - 框内外描边覆盖率（`glow_halo`）：相邻绿牌的面会在别人的框里发光，真牌河与自家牌河都会误报；
   - 牌面大小的描边连通块（`marked_discard`）：会把普通索子牌判成高亮，三次试验全部指错座位；
   - 青色/高亮色扫描：被桌面、立绘和面板的大片青蓝像素淹没。

   为避免误判，以上全部只记录不采用。下一步建议：为 `highlighted_discard()` 增加“当前牌河的格子位置”输入，在未识别到牌的格子上单独检测描边，而不是只在已识别牌框上测量。

2. **响应来源仍可能被规则层拒绝**：`reports/no-draw-call-discard/review-path.json` 记录，图二即使人工指定“刚出牌者=上家、可吃”仍会报“当前按钮与规则合法动作没有交集”，因为按当前识别出的手牌吃不到那张九索。这说明这些画面里**手牌或牌河本身还缺牌**，属于阶段二识别缺口（图三则直接报自己牌河不完整）。来源识别修好之后，这一步仍需要更完整的牌面。

3. **高亮牌的牌种**：即使座位确定，若末张未被识别，响应牌种仍需人工在核对界面指定。

4. **自己多组副露时“刚完成的吃碰”**：需要跨帧记忆（面板连续运行时可记录上一帧的鸣牌），目前需要用户在核对界面勾选“刚完成的那一组”。

5. **核对面板可以指定来源**（已核对代码路径）：`app/ui/advice.py` 的核对对话框提供“刚出牌者”和“可吃/碰/杠/和”勾选，`call_discard` 时取最后一组副露作为刚完成的鸣牌，并写入 review 的 `context`。这是当前唯一能绕过高亮检测、拿到建议的入口。

## 结论

- 已修：供托/本场为零不再阻塞、牌局文字同值即采用、吃按钮按规则确定来源、提示信息指明操作入口。
- 未修：高亮弃牌的自动定位。图二/图三的自动化建议仍需先解决“被鸣牌未被识别成牌河牌”和“该画面手牌/牌河缺牌”两项识别问题。
